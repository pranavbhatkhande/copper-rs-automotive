Executive Summary

Copper-rs claims to provide deterministic execution, unified logging, and sub-microsecond latency for robotics task graphs. After deep, line-by-line audit of the core runtime, proc-macro code generation, clock system, unified logging, replay/resimulation infrastructure, and automotive extensions, this report concludes that copper-rs delivers genuine structural determinism with clearly defined boundaries.

The determinism is not a marketing claim—it is enforced through compile-time code generation, a fixed execution plan, preallocated data structures, and a verified record/replay pipeline. There are important boundary conditions where determinism degrades, documented below.

1 Architecture of Determinism

1.1 Design Philosophy

Copper-rs is built on: "A robot is a static thing." This means:

  • Static task graph — declared in RON config, parsed and wired at compile time
  • Compile-time execution plan — BFS topological sort produces a fixed sequential order
  • No dynamic dispatch — tasks are a generated tuple (T0, T1, T2, ...)
  • No runtime graph mutation — topology frozen after compilation
  • Preallocated communication — CopperList is a typed tuple in a ring buffer
💡 Key Insight
The execution model resembles a synchronous dataflow graph — not pub/sub middleware. This is the strongest foundation for determinism available without formal verification.

1.2 The Execution Plan

Key file: core/cu29_runtime/src/curuntime.rs, lines 980–1060

The compute_runtime_plan() function generates execution order at compile time:

1. Collect all Source nodes (no incoming edges) in node_indices() order → Deterministic 2. BFS from each source using petgraph::Bfs → visits neighbors in insertion order → Deterministic 3. For each node: collect incoming edges, sort by edge index → Deterministic 4. Sort task inputs by connection ID (sort_inputs_by_cnx_id) → Deterministic 5. Assign output indices sequentially → Deterministic 6. Verify all nodes are planned (fail compilation otherwise) → Safety net

1.3 The Generated Run Loop

Key file: core/cu29_derive/src/lib.rs, lines 2514–2573

The proc macro generates run_one_iteration() with this exact structure:

fn run_one_iteration(&mut self) -> CuResult<()> {
    // 1. Pre-explode runtime fields (avoid partial borrows)
    // 2. Execute ALL preprocess() calls (bridges, then tasks)
    // 3. Allocate CopperList from ring buffer
    // 4. For EACH step in execution plan (sequential, single-thread):
    //    a. Record execution marker
    //    b. Read inputs from CopperList slots (immutable)
    //    c. Call task.process(ctx, &input, &mut output)
    //    d. Freeze task state into keyframe if interval hit
    // 5. Serialize CopperList to unified log
    // 6. Execute ALL postprocess() calls
}
✅ Critical Property
Steps execute sequentially, in a single thread, in compile-time-determined order. No parallelism, no async, no scheduling jitter. Each task sees a consistent snapshot of all its inputs.

1.4 The CopperList: Zero-Copy Message Bus

Key file: core/cu29_runtime/src/copperlist.rs

  • Generated tuple type: (CuMsg<SensorData>, CuMsg<ControlCmd>, CuMsg<()>)
  • Managed by CuListsManager<P, N> — a preallocated ring buffer
  • Allocated via alloc_zeroed at startup — never reallocated
  • Monotonically increasing IDs
  • State machine: Free → Initialized → Processing → DoneProcessing → BeingSerialized → Free

💡 How Replay Uses the Clock
Recorded process_time metadata in each CuMsg captures clock readings. During replay, the mock clock is synchronized to the recorded timestamp before each CopperList is re-executed. Tasks re-execute with identical timing.

4 Replay & Resimulation — The Proof

The Four-Part Determinism Contract

File: examples/cu_caterpillar/src/determinism_test.rs

This CI-verified test enforces:

Contract #1: record_A.copperlists == record_B.copperlists (identical independent runs) Contract #2: record_A.keyframes == record_B.keyframes (identical state snapshots) Contract #3: record_A.copperlists == resim(A).copperlists (replay matches original) Contract #4: record_A.keyframes == resim(A).keyframes (replay state matches original) Verified via byte-for-byte comparison of bincode-encoded streams.

How Replay Works

  1. Record: Run with mock clock, sim callbacks stub sources/sinks. Log CopperLists + keyframes.
  2. Resim: For each recorded CopperList:
    • Set mock clock to recorded process_time.start
    • Inject recorded source output via sim callback
    • Runtime executes task graph (middle tasks run real process())
    • Sinks stubbed for deterministic metadata
  3. Verify: Byte-for-byte comparison of all CopperLists and keyframes.

Keyframe System

Keyframes snapshot all task states at configurable intervals. During replay:

  • lock_keyframe() preloads a recorded keyframe verbatim
  • forced_timestamp overrides the keyframe timestamp
  • Tasks implement Freezable — freeze() serializes, thaw() restores

5 Identified Determinism Gaps

🔴 Gap 1: CuAsyncTask — Threading Non-Determinism

File: core/cu29_runtime/src/cuasynctask.rs

CuAsyncTask wraps a CuTask and runs process() on a rayon::ThreadPool. Background task completion timing depends on thread scheduling. The ready_at gating mechanism restores determinism during replay, but live execution order is non-deterministic.

Recommendation: Do not use CuAsyncTask for safety-critical deterministic paths.

🔴 Gap 2: External I/O — Kernel-Dependent Timing

Files: cu_can/src/socketcan.rs, cu_someip/src/source.rs

Source tasks that read from CAN sockets (libc::read) or UDP sockets (libc::recv) depend on kernel scheduling and bus/network traffic. This is the expected and correct boundary of determinism.

Key insight: Copper's architecture places all non-determinism at source task boundaries. Everything downstream is deterministic given identical source outputs. Replay handles this by injecting recorded outputs.

🟡 Gap 3: Floating-Point Cross-Platform Portability

File: examples/cu_vehicle_sim/src/ecu_radar.rs

The radar simulation uses f64 transcendental functions (sin, cos). IEEE 754 basic operations are deterministic across platforms, but transcendental functions are NOT required to be correctly rounded — implementations differ between libm versions and architectures.

On the same binary on the same architecture, results are deterministic. Cross-platform, they may differ.

Recommendation: Use lookup tables or polynomial approximations for safety-critical paths.

🟡 Gap 4: HashMap in Configuration

File: core/cu29_runtime/src/config.rs

ComponentConfig wraps hashbrown::HashMap. Iteration order is non-deterministic. However, this is used only in configuration parsing — the execution plan is built from graph structure, not HashMap iteration. No impact on runtime determinism.

8 Recommendations

For copper-rs-automotive

  1. Add a determinism regression test for automotive tasks. Create an equivalent of the caterpillar test with mock CAN inputs.
  2. Use mock mode in CI. Run with --features mock to eliminate kernel I/O non-determinism.
  3. Replace sin()/cos() in safety-critical paths with lookup tables or documented polynomial approximations.
  4. Eliminate hot-path Vec allocations in bus_spy.rs and SOME/IP SD parsing.
  5. Document the determinism boundary explicitly in AGENT-AUTOMOTIVE.md.

For upstream copper-rs

  1. Formalize CuAsyncTask contract — document that background tasks introduce scheduling non-determinism.
  2. Consider #[deny_alloc] hot-path annotation alongside the existing rtsan feature.
  3. Address unsafe lifetime in memmap.rs:324 with explicit lifetime parameters.
