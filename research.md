## Executive Summary

Copper-rs claims to provide **deterministic execution, unified logging, and sub-microsecond latency** for robotics task graphs. After a deep, line-by-line audit of the core runtime, proc-macro code generation, clock system, unified logging, replay/resimulation infrastructure, and automotive-specific extensions, **this report concludes that copper-rs delivers genuine structural determinism** with clearly defined boundaries.

The determinism is **not a marketing claim**—it is enforced through compile-time code generation, a fixed execution plan, preallocated data structures, and a verified record/replay pipeline. However, there are important **boundary conditions** where determinism degrades, particularly around external I/O, floating-point cross-platform portability, and the `CuAsyncTask` threading model.

### Verdict

| Dimension | Rating | Notes |
|-----------|--------|-------|
| **Execution order determinism** | ✅ **Strong** | Compile-time BFS topological sort, edge-sorted inputs |
| **Message passing determinism** | ✅ **Strong** | Preallocated ring buffer, zero-copy, statically typed tuple |
| **Logging/serialization determinism** | ✅ **Strong** | Ordered mmap sections, bincode standard config |
| **Replay/resimulation fidelity** | ✅ **Strong** | Byte-for-byte verified in CI (caterpillar test) |
| **Clock determinism in replay** | ✅ **Strong** | Mock clock with `AtomicU64`, injectable timestamps |
| **Memory allocation determinism** | ✅ **Strong** | No heap allocs on hot path in core runtime |
| **Automotive task determinism** | ⚠️ **Conditional** | Pure-logic tasks deterministic; I/O tasks non-deterministic at boundaries |
| **Cross-platform FP determinism** | ⚠️ **Conditional** | IEEE 754 compliant, but transcendental functions (sin/cos) vary by arch |
| **Async/background task determinism** | ⚠️ **Weak** | Thread scheduling introduces non-determinism; timing-gated output surfacing |

## 1. Architecture of Determinism

### 1.1 Design Philosophy

Copper-rs is built around the principle: **"A robot is a static thing."** The framework enforces:

- **Static task graph**: Declared in RON config, parsed and wired at compile time via `#[copper_runtime(config = "...")]`
- **Compile-time execution plan**: BFS topological sort generates a fixed, sequential execution order
- **No dynamic dispatch**: Tasks are a generated tuple `(T0, T1, T2, ...)`, not trait objects
- **No runtime graph mutation**: The topology cannot change after compilation
- **Preallocated communication**: The `CopperList` is a statically-typed tuple of `CuMsg<T>` preallocated in a ring buffer

This is the strongest foundation for determinism available without a formal verification language. The execution model resembles a synchronous dataflow graph more than a traditional publish-subscribe middleware.

### 1.2 The Execution Plan (Compile-Time)

**Key file:** `core/cu29_runtime/src/curuntime.rs`, lines 980–1060

The `compute_runtime_plan()` function generates the execution order:

1. **Collect all Source nodes** (nodes with no incoming edges) in `node_ids()` order — which is `petgraph::StableDiGraph::node_indices()` order, i.e., insertion order. **Deterministic.**
2. **BFS from each source** using `petgraph::visit::Bfs` — which visits neighbors in edge-insertion order for `StableDiGraph`. **Deterministic.**
3. **For each node visited**, incoming edges are collected and **sorted by edge index** (`edge_ids.sort()` at lines 844, 890). **Deterministic.**
4. **Task inputs are sorted by connection ID** (`sort_inputs_by_cnx_id` at line 944). **Deterministic.**
5. **Output indices assigned sequentially** (line 984: `next_culist_output_index`). **Deterministic.**
6. **Missing node check**: If any node is not in the plan, compilation fails (line 1048). **Safety net.**

**Conclusion:** The execution plan is fully deterministic given the same RON config file.

### 1.3 The Generated Run Loop

**Key file:** `core/cu29_derive/src/lib.rs`, lines 2514–2573

The `run_one_iteration()` method is generated by the proc macro. Its structure is:

```
1. Pre-explode runtime fields (avoid partial borrows)
2. Execute ALL preprocess() calls (bridges first, then tasks)
3. Allocate a CopperList from the ring buffer
4. Set CopperList state to Processing
5. For EACH step in the execution plan (sequential, in plan order):
   a. Record execution marker for monitoring
   b. Read input messages from CopperList tuple slots (immutable borrows)
   c. Call task.process(ctx, input, output) — writes to output slot
   d. Freeze task state into keyframe (if keyframe interval hit)
6. Collect monitoring metadata
7. Serialize CopperList to unified log
8. Execute ALL postprocess() calls (tasks first, then bridges)
```

**Critical observation:** Steps 5a–5d execute **sequentially, in a single thread, in the compile-time-determined order**. There is no parallelism, no async, no scheduling jitter. Each task sees a consistent, immutable snapshot of all its inputs because earlier tasks have already written their outputs to fixed tuple slots.

### 1.4 The CopperList: Zero-Copy Message Bus

**Key file:** `core/cu29_runtime/src/copperlist.rs`

The `CopperList<P>` is the heart of inter-task communication:

- `P` is a **generated tuple type** (e.g., `(CuMsg<SensorData>, CuMsg<ControlCmd>, CuMsg<()>)`)
- Managed by `CuListsManager<P, N>` — a **preallocated ring buffer** of `N` CopperLists
- Allocated via `alloc_zeroed` at startup (line 141), **never reallocated**
- Each CopperList has a **monotonically increasing ID** (`current_cl_id`, line 201)
- State machine: `Free → Initialized → Processing → DoneProcessing → BeingSerialized → Free`

**No heap allocation on the hot path.** Messages are written directly into tuple slots via mutable references. There are no channels, no queues, no dynamic dispatch.

## 2. Clock System

**Key file:** `core/cu29_clock/src/lib.rs`

### 2.1 Real Clock

- Uses **hardware cycle counters** (TSC on x86_64, `cntvct_el0` on aarch64, `mcycle` on RISC-V)
- Calibrated against the system RTC at startup
- `CuTime` = `CuDuration` = `u64` nanoseconds — no floating point
- Monotonic by construction (hardware counters don't go backward)

### 2.2 Mock Clock (Critical for Determinism)

```rust
pub fn mock() -> (RobotClock, RobotClockMock) {
    let (clock, mock_state) = InternalClock::mock();
    // mock_state is Arc<AtomicU64>
    ...
}
```

- `RobotClockMock::set_value(u64)` — sets absolute time
- `RobotClockMock::increment(CuDuration)` — advances time
- All clones of a `RobotClock` share the same `Arc<AtomicU64>` — **globally consistent**
- Used in simulation mode and replay to inject deterministic timestamps

### 2.3 Determinism Assessment

- **Real mode:** Clock is monotonic but real-time; execution wall-clock times vary. **Not deterministic** across runs.
- **Mock mode (sim/replay):** Clock is fully user-controlled. **Fully deterministic.**
- **Key insight:** The recorded `process_time` metadata in each `CuMsg` captures the clock readings. During replay, these are restored from the log, and the mock clock is synchronized. The task graph re-executes with identical timing.

## 3. Unified Logging System

**Key files:** `core/cu29_unifiedlog/src/lib.rs`, `core/cu29_unifiedlog/src/memmap.rs`

### 3.1 Write Path

1. **Memory-mapped slab files** (e.g., `app_0.copper`, `app_1.copper`)
2. **Sections** allocated within slabs, page-aligned
3. **LogStream** wraps a section for append-only writes using `bincode::encode_into_slice` with **standard config**
4. **Section ordering** guaranteed by `sections_offsets_in_flight` vector — flushes happen in allocation order
5. **Multi-slab rollover** preserves ordering via sequential file naming

### 3.2 Read Path

1. Sequential scanning through mmap buffers
2. Section headers validated by magic number
3. Entries decoded with `bincode::decode_from_std_read` (standard config) — **byte-identical deserialization**
4. Lazy iterator pattern — entries on demand

### 3.3 Determinism Assessment

- **Write ordering: ✅ Deterministic** — single-threaded within Mutex, sequential allocation
- **Serialization: ✅ Deterministic** — bincode standard config always produces identical bytes for identical inputs
- **Read ordering: ✅ Deterministic** — sequential scan, no random access
- **Cross-slab ordering: ✅ Deterministic** — sequential file numbering

## 4. Replay & Resimulation

### 4.1 The Determinism Contract

**Key file:** `examples/cu_caterpillar/src/determinism_test.rs`

The test enforces a **four-part contract**:

```
1) record_A.copperlists == record_B.copperlists   (identical independent runs)
2) record_A.keyframes   == record_B.keyframes      (identical task state snapshots)
3) record_A.copperlists == resim(A).copperlists    (replay matches original)
4) record_A.keyframes   == resim(A).keyframes      (replay state matches original)
```

This is verified via **byte-for-byte comparison** of bincode-encoded streams:

```rust
fn assert_streams_equal(label_a: &str, a: &[Vec<u8>], label_b: &str, b: &[Vec<u8>]) {
    assert_eq!(a.len(), b.len(), ...);
    for (i, (item_a, item_b)) in a.iter().zip(b.iter()).enumerate() {
        if item_a != item_b { panic!(...); }
    }
}
```

### 4.2 How Replay Works

1. **Record phase**: Run app with mock clock, sim callbacks for source/sink stubs. Log CopperLists + keyframes.
2. **Resim phase**: Read recorded CopperLists. For each:
   a. Set mock clock to the recorded `process_time.start` of the source output
   b. Inject the recorded source output into the sim callback
   c. Let the runtime execute the task graph (middle tasks run their real `process()` methods)
   d. Stub sinks to produce deterministic metadata
3. **Verify**: Compare all CopperLists and keyframes byte-for-byte.

### 4.3 Keyframe System

**Key file:** `core/cu29_runtime/src/curuntime.rs`, lines 108–197

- **KeyFrame** = snapshot of all task states at a given CopperList ID
- Generated every `keyframe_interval` CopperLists
- Tasks implement `Freezable` — `freeze()` serializes state, `thaw()` restores it
- During replay, `lock_keyframe()` preloads a recorded keyframe verbatim
- `forced_timestamp` overrides the keyframe timestamp for deterministic replay

### 4.4 Remote Debug Replay

**Key file:** `core/cu29_runtime/src/remote_debug.rs`

The remote debug API supports seeking to arbitrary positions in the log:

1. Find nearest keyframe before target position
2. Restore task state from keyframe
3. Replay CopperLists forward to target position
4. Mock clock synchronized at each step

This is a **higher-power replay path** for interactive debugging, and it maintains the same determinism guarantees.

## 5. Identified Determinism Gaps & Risks

### 5.1 🔴 CuAsyncTask — Threading Non-Determinism

**File:** `core/cu29_runtime/src/cuasynctask.rs`

`CuAsyncTask` wraps a `CuTask` and runs its `process()` method on a `rayon::ThreadPool`:

```rust
self.tp.spawn_fifo({
    // ... clone input, lock task, call process() ...
});
```

- The background task runs **asynchronously** — its completion time depends on thread scheduling
- The main loop polls for results; output surfaces only when `ready_at` time has passed
- **`ready_at` is recorded in metadata** — replay can honor recorded completion times

**Risk:** In real-time execution, the order in which background tasks complete relative to the main loop is non-deterministic. The `ready_at` gating mitigates this for replay, but **live execution order is non-deterministic**.

**Mitigation:** Use `CuAsyncTask` only for tasks where the output timing can tolerate scheduling jitter. Do not use it for safety-critical deterministic paths.

### 5.2 🔴 External I/O — Kernel-Dependent Timing

**Automotive files:** `components/tasks/cu_can/src/socketcan.rs`, `components/tasks/cu_someip/src/source.rs`

- `libc::read()` on CAN sockets — frame arrival depends on bus traffic and kernel scheduling
- `libc::recv()` on UDP sockets — packet arrival is network-dependent
- `libc::write()`/`libc::sendto()` — write latency varies with kernel buffer state

**This is the expected boundary of determinism.** Source tasks are the entry points for non-deterministic real-world data. The determinism contract handles this by **recording source outputs** and replaying them verbatim during resimulation.

**Key insight:** Copper's architecture places all non-determinism at **source task boundaries**. Everything downstream (transforms, sinks) is deterministic given identical source outputs.

### 5.3 🟡 Floating-Point Cross-Platform Portability

**Automotive file:** `examples/cu_vehicle_sim/src/ecu_radar.rs`

The radar ECU simulation uses `f64` trigonometric functions:
```rust
track.lat_dist += 0.01 * ((self.tick as f64 * 0.1).sin());
track.rel_accel = 0.5 * ((self.tick as f64 * 0.05 + track.long_dist * 0.01).sin());
```

- IEEE 754 basic operations (+, -, *, /) are **deterministic across platforms** with the same rounding mode
- **Transcendental functions** (`sin`, `cos`, `exp`, `log`) are **NOT required by IEEE 754 to be correctly rounded** — implementations may differ between libm versions, compilers, and architectures
- On the **same binary on the same architecture**, results are deterministic

**Risk:** If you compile on x86_64 and deploy on aarch64, floating-point results may differ slightly. This would break the byte-for-byte determinism contract.

**Mitigation:** For cross-platform determinism, avoid transcendental functions in task `process()` methods, or use a deterministic math library (e.g., `rug` with MPFR, or fixed-point arithmetic).

### 5.4 🟡 HashMap Usage in Configuration

**File:** `core/cu29_runtime/src/config.rs`

`ComponentConfig` wraps `hashbrown::HashMap<String, Value>`. HashMap iteration order is non-deterministic in general.

**Assessment:** This is used only in **configuration parsing** (not on the hot path). The execution plan is built from the graph structure, not from HashMap iteration. **No impact on runtime determinism.**

However, if any code iterates a `ComponentConfig` to produce output that affects behavior (e.g., ordering of keys), that code would be non-deterministic. Current code does not do this.

### 5.5 🟡 Heap Allocations in Automotive Tasks

- `examples/cu_vehicle_sim/src/bus_spy.rs:62` — `Vec::new()` in `process()` for signal string building
- `components/tasks/cu_someip/src/sd.rs:51` — `Vec::new()` in SOME/IP SD entry parsing

**Risk:** Heap allocations introduce allocator-dependent latency variance. Not a correctness issue for determinism, but violates the "no alloc on RT path" principle.

### 5.6 🟢 Petgraph BFS Determinism

`petgraph::StableDiGraph` with `Bfs` visits neighbors in **edge storage order**, which for `StableDiGraph` is insertion order. Since edges are added in RON config parsing order, and RON parsing is deterministic, BFS traversal is deterministic.

Verified by examining `petgraph` source: `Bfs` uses `neighbors()` which iterates the adjacency list in insertion order for `StableDiGraph`.

## 7. Comparison to Industry Standards

### 7.1 vs. ROS 2

| Feature | Copper-rs | ROS 2 |
|---------|-----------|-------|
| Execution order | Compile-time fixed | Runtime executor-dependent |
| Message passing | Zero-copy tuple slots | DDS pub/sub (heap alloc) |
| Replay | Byte-for-byte verified | rosbag replay (timing approximation) |
| Clock | Mock-injectable `AtomicU64` | `use_sim_time` parameter |
| Determinism proof | CI-verified contract test | No formal verification |

### 7.2 vs. AUTOSAR Adaptive

| Feature | Copper-rs | AUTOSAR Adaptive |
|---------|-----------|------------------|
| Scheduling | Static BFS order | Deterministic scheduling specified |
| Communication | Direct tuple access | ara::com (SOME/IP based) |
| Logging | Unified binary log | DLT (Diagnostic Log and Trace) |
| Replay | Built-in resimulation | External tooling required |

### 7.3 vs. Game Engine Determinism (e.g., lockstep)

Copper-rs's model is closest to **lockstep deterministic simulation** used in multiplayer games:
- Fixed update order
- Deterministic inputs (mock clock, recorded sources)
- State snapshots (keyframes) for resync

The key difference: game engines typically enforce fixed-point math for cross-platform determinism. Copper-rs does not enforce this — it's a documented gap.

## 8. Recommendations

### 8.1 For the copper-rs-automotive Project

1. **Add a determinism regression test for automotive tasks.** The caterpillar test exists for the upstream example. Create an equivalent for the vehicle simulation that verifies record/replay byte-for-byte equality with mock CAN inputs.

2. **Use mock mode in CI.** All automotive task tests should run with `--features mock` to eliminate kernel I/O non-determinism.

3. **Replace `sin()`/`cos()` in safety-critical paths.** For the radar ECU simulation, consider lookup tables or polynomial approximations with documented precision guarantees.

4. **Eliminate hot-path Vec allocations.** In `bus_spy.rs`, use a fixed-size buffer. In SOME/IP SD parsing, pre-allocate or use an iterator pattern.

5. **Document the determinism boundary.** Make explicit in the automotive AGENTS.md that:
   - Source/sink tasks with real I/O are non-deterministic at the kernel boundary
   - Replay determinism requires mock clock + recorded source outputs
   - Cross-platform FP determinism is not guaranteed for transcendental functions

### 8.2 For Upstream copper-rs

1. **Formalize the `CuAsyncTask` determinism contract.** Document that background tasks introduce scheduling non-determinism and specify how `ready_at` gating restores determinism during replay.

2. **Consider adding a `#[deny_alloc]` hot-path annotation.** The `rtsan` feature already provides real-time sanitization. Extend it to verify no allocations occur in `process()` methods.

3. **Unsafe lifetime in `memmap.rs:324`** — while currently safe due to ownership chain, adding explicit lifetime parameters would improve safety guarantees.

### Mental Model

Think of copper-rs as: **"A game engine for robots where the scene graph is a task graph and the engine is generated from RON config."**

The determinism model is: **"Lockstep simulation with recorded inputs."** Given identical inputs (source task outputs), the entire pipeline produces byte-identical results. This is verified in CI.

The boundary of determinism is: **"Source tasks are the border between the deterministic world and the non-deterministic physical world."** Everything inside the graph is deterministic. Everything at the edges (sensors, actuators, network) is not — but it's recorded for replay.
